Getting Started with Automation30

Everything you need to download, set up, and run your first engagement with the Automation30 framework.

⚠ Prerequisites

Before you begin, make sure you have both of the following installed and ready:

⚡ Claude Code + License
Automation30 runs inside Claude Code. Download it and ensure you have an active Claude license (Pro or above). The framework can also run on GitHub Copilot, Cursor, or Windsurf, though Claude Code is recommended for full compatibility.
⇩ Download Claude Code
🕐 Git
Git must be installed and available in your terminal. The framework uses Git for version control and branch management during sprint cycles. Install the latest version from the official Git website.
⇩ Download Git
1
Download the Automation30 Complete Pack
The complete pack contains all files needed to run the framework — prompt files, skills, references, templates, and configuration. The only thing not included is your project-specific input (transcript/spec, context files, etc.) which you bring to each engagement.
ⓘ Once downloaded, extract the pack into your project folder. Do not rename or restructure the folders — the framework relies on specific file paths to locate skills and prompts.
⇩ Click to Visit Website
On the website, find the Automation30 — AI Native Development Kit card and click Open on the right to launch the framework.
📖 Also open the Docs while you're there
A complete offline reference for the framework — covering context efficiency, model routing, and cost governance. Everything you need to understand and run the AI Native Development Kit.
Click Open on the DOCS card to access the full reference.
2
Set Up Your Project Folder & Add Your Inputs
Extract all files from the Complete Pack into your project folder, keeping the folder structure intact. Then add your chosen input documents — the transcript/spec, context files, or Claude Design export you’ll be working from — into the same folder so the framework can read them.
ⓘ Which input documents you add depends on the Input Method you plan to use. See the three options and what each expects under Input Methods in the Execution Methods tab →
3
Customize the Phase Prompts
The prompts/ folder holds one file per phase (01-establish-strategy.md through 05-simplified-ai-operations.md). Each file is a sequence of prompts the framework runs in order. Before you begin, open these files and tailor them to your engagement — adjust the input documents each prompt reads from, and add or remove any outputs you want produced. Start with 01-establish-strategy.md, which drives the strategy and specification phase.
ⓘ Every prompt declares its Inputs near the top. Point these at the actual files you’re providing. If your input is a meeting transcript plus a summary, set both as the elicitation source — as highlighted below.
Example — inputs edited to use a transcript + a summary:
The highlighted meeting_transcript.txt and meeting_summary.txt are the two input files — swap these paths for whatever documents you bring to the engagement.
4
Run the First 6 Prompts — Build Your Source of Truth
Upload your project folder into Claude Code, then run 01-establish-strategy.md. This drives the first six prompts, which produce the six core specification files. These specs are the brain of the framework — every later phase reads from them, so review each one carefully and correct anything before you move on. Nothing downstream is better than what you lock in here.
The 6 files generated (in order):
1
program.mdProgram charter — goals, scope, stakeholders
2

3
design.mdTechnical architecture & stack
4
ui-ux.mdUI/UX specification
5
database.mdSchema, relationships, migrations
6
api.mdEndpoints, auth, request/response contracts
How each prompt runs:
1
Pre-generation summary — the prompt presents a short bulleted summary of what it will produce and waits.
↓
2
You reply NEXT to approve — or send corrections first.
↓
3
File generated — followed by a post-generation summary of what was written.
↓
4
You reply CONFIRM to lock it in and move to the next prompt.
Repeat this cycle for all six prompts. Read each summary properly before you CONFIRM — every later phase inherits these files, so correcting something now is far easier than after the framework has built on top of it.
ⓘ Prompt 7 runs SkillFlow, which recommends the skills for your later phases. From there you’ll pick how the framework actually runs — see Execution Modes in the Execution Methods tab →
💡 Good to know
Got a spec wrong after confirming? You don’t have to start over — just re-run that single prompt and it regenerates only that file.
At the end of all six, you’ll hold a complete Phase 1 specification baseline — the full source of truth the framework builds everything else on top of, ready for SkillFlow.

One to watch for: in 03-platform-enablement.md, DevCopilot asks whether to generate the whole codebase in a single pass, or epic by epic with a review after each epic before the next begins.
✓
That’s it — here’s what you’ll have built
Once you’ve worked through all the phases, your project folder holds a complete, traceable delivery:
specs/ Your source of truth — program.md, knowledge.md, design.md, ui-ux.md, database.md, api.md, plus spec.md and tasks.md.
src/ & tests/ The generated codebase and its test suite, built directly against the specs.
artifacts/ Planning & validation trail — task breakdown, traceability, test & coverage results, decision ledger, and release plans.
operate/ The operations layer — cost governance, drift monitoring, runbooks, and incident logs for the live system.

Input Methods
I1
Transcript / Spec Document Only
Skills elicit everything through questions
First engagementNo prior context
Recommended ▶
What it is
You provide a single discovery input — this can be a session transcript/spec, a BRD, or any requirements/spec document the client has shared. All spec and design decisions are elicited by the skills through structured questions — nothing is assumed. Every group in every skill runs its full elicitation flow.
Where it goes
Drop transcript.md (or your session notes) in the project root. No context/ folder is required.
How it affects the process
All elicitation questions are asked in full across spec-design, spec-uiux, and dev-copilot. Expect longer sessions. Output quality depends entirely on how well the transcript/spec captured client intent.
How to invoke
Open prompts/01-establish-strategy.md and follow from Prompt 1. No additional setup needed.
Example scenario
First call with a new client. You have a transcript/spec but the client hasn't shared any preferences, brand guidelines, or design files yet. The skills will ask and document everything from scratch.
I2
Transcript/Spec + Context Files
Skills skip covered groups, read from your files
Standard runcontext/ folder
Recommended ▶
What it is
You provide the transcript/spec plus up to three client-supplied context files: design-preferences.md (tech stack and architecture choices), ux-reference.* (brand, colors, components), and org-standards.md (coding conventions and constraints). Skills read these files at Step 0 and skip elicitation for any group already answered.
Where it goes
All three files go in the context/ folder at project root. Any or all can be provided — missing files trigger a one-time ask before proceeding normally.

  • context/design-preferences.md → read by spec-design, spec-generation
  • context/ux-reference.* → read by spec-uiux
  • context/org-standards.md → read by dev-copilot
How it affects the process
Covered elicitation groups are skipped entirely. Skills present a summary of what was inferred from the file and ask for confirmation before proceeding. Only gaps are elicited. Sessions run noticeably faster.
How to invoke
Create the context/ folder, drop files in, then run prompt files as normal. The Context Check block at the start of 01-establish-strategy.md detects and loads them automatically.
Example scenario
Client has existing tech stack decisions (FastAPI, Next.js, AWS) and a brand style guide. They share these as documents before the engagement starts. The skills skip those elicitation blocks and move straight to gaps.
I3
Transcript/Spec + Context + Claude Design Export
Design tokens extracted directly from the mockup file
Full stack input.html / .zip
Recommended ▶
What it is
Everything from I2, plus a Claude Design export — an HTML or zip file produced when you export a UI mockup from Claude's built-in design tool. The file encodes the entire design system as CSS variables, class names, and component markup. The framework parses this directly instead of asking about colors, typography, and components.
Where it goes
Drop the .html or .zip file anywhere inside the context/ folder. It can be named anything — the skills detect it by extension. It supplements or replaces ux-reference.* if both are present.
How it affects the process
spec-uiux extracts CSS variables (colors, spacing, radius, shadows) and component markup to build the design token section automatically. dev-copilot reads the same file to match generated frontend code to the extracted styles. Color and component elicitation is fully skipped. A summary is presented for confirmation before proceeding.
How to invoke
Export from Claude Design (“Download” → HTML or zip). Drop in context/. Run prompt files normally — the Step 0 block in spec-uiux and dev-copilot detects it automatically.
Example scenario
Client approved a Claude Design mockup before development begins. You export the file and drop it in context/. The generated UI spec and all frontend code will match the approved mockup — no manual design translation needed.
Execution Modes
E1
Manual — All Prompts in Sequence
Full HITL control, prompt by prompt across all 5 files
Most controlNew engagements
Recommended ▶
What it is
You work through all five prompt files sequentially, responding to each prompt with NEXT to generate output and CONFIRM to approve before moving on. Every output is reviewed. Nothing advances without your sign-off.
Where it goes
The five prompt files in order: 01-establish-strategy.md → 02-data-readiness.md → 03-platform-enablement.md → 04-ai-solution-deployment.md → 05-simplified-ai-operations.md
How it affects the process
All HITL gates are active. You see every output before it is accepted. Embedded Recommendation Gate in Prompt 8 of file 01 lets you decide which skills to run downstream. The skillflow_skip.md gate file is always written after this point, controlling all subsequent prompts.
How to invoke
Open prompts/01-establish-strategy.md and paste or reference Prompt 1 into a Claude Code session. Follow the NEXT/CONFIRM pattern throughout. Resume any time from where you left off.
Example scenario
First engagement with a new client in an unfamiliar domain. You want to review every spec and catch anything that doesn't match the client's mental model before it propagates downstream.
E2
SkillFlow-Recommended Run
Run only the skills SkillFlow recommends; gate file controls the rest
EfficientTypical run
Recommended ▶
What it is
After running SkillFlow (Prompt 7 in file 01), the Recommendation Gate presents a plan: which skills are essential, which are optional, and which are not relevant. You choose A (follow the plan), B (run everything), or C (decide skill by skill). A skillflow_skip.md file is always written based on your choice, and all downstream prompts read it to skip non-relevant skills automatically.
Where it goes
skillflow_skip.md is written to the project root after the Recommendation Gate. All prompts from 9 onward in file 01, and all prompts in files 02–05, check this file before executing. No manual intervention is needed after the gate.
How it affects the process
Non-recommended skills are skipped with a logged note. Optional skills are included or excluded based on your gate response. You can restart the session at any prompt and the same skip list applies. Sessions run significantly faster for scoped engagements.
How to invoke
Run through Prompt 7 (SkillFlow) in file 01. When the Recommendation Gate appears, answer A, B, or C. The gate writes skillflow_skip.md and the rest of the pipeline self-manages from there.
Example scenario
Typical client engagement where only 6 of 12 skills are relevant. SkillFlow recommends the right 6. You choose A, the skip file is written, and the rest of the session runs without you having to manually skip anything.
E3
Skill-Orchestrator CLI
Wave-based execution with dependency ordering and rework routing
AutomatedLarge engagementsResumable
Recommended ▶
What it is
A CLI tool that groups skills into dependency-ordered waves and executes them with explicit HITL gates at each wave boundary. The orchestrator tracks state after every record command, supports rework cycles when a skill output is rejected, and can resume from any point without re-running completed work.
Where it goes
Run from the project root via the Python module. State is persisted to a local file after each record call. Commands:

  • python -m skill_orchestrator.cli init — initialize a run
  • next — get the next wave to execute
  • record — save output and advance state
  • report — generate progress summary
How it affects the process
The orchestrator decides execution order (Wave 0 = no dependencies, subsequent waves block on predecessors). Independent skills in the same wave can run in parallel. Rejected outputs are routed back for rework. The engine tracks APPROVED / REJECTED / PENDING states and won't advance until gates clear.
How to invoke
Run init, then call next to get the first wave. Execute the listed skills, then record each result. At each gate, approve or reject. Call next again to advance. If interrupted, restart and call next — completed waves are skipped.
Example scenario
Large engagement with 10 skills and complex interdependencies — spec-knowledge must complete before spec-api and spec-database. The orchestrator handles ordering automatically and ensures nothing runs out of sequence.
E4
Conductor Dispatch
Task-level assignment with live sprint board tracking
Build phasePost Gate-1Multi-builder
Recommended ▶
What it is
Triggered after Gate 1 is cleared, Conductor operates at the task level (not skill level). It assigns individual tasks to builders, generates a live sprint board, and tracks status as DISPATCHED (ready), BLOCKED (dependency unmet), or ESCALATED (HITL blocker). It is separate from the Skill-Orchestrator and takes over once specs are approved and build work begins.
Where it goes
Triggered by saying “Run Conductor” or “Dispatch sprint board” in the session after Gate 1 clearance. Conductor reads the approved specs and SpecFlow cluster assignments to build its task graph.
How it affects the process
Tasks with unresolved HITL blockers go to the HITL Gate Queue and wait for clearance before dispatching. Assumption blockers escalate. Conductor re-runs as blockers resolve, progressively dispatching more tasks. The sprint board updates live.
How to invoke
Complete Phase 1 (spec generation) and Gate 1 approval. Then trigger Conductor in the session. It runs pre-flight validation first — halts if Gate 1 isn't cleared, required artifacts are missing, or critical HITL blockers remain unresolved.
Example scenario
Engagement has moved into build. Three builders are working in parallel. Conductor assigns tasks based on dependency order, surfaces which builders are blocked, and escalates assumption conflicts to the POD Lead before they cause rework.
E5
Ad-hoc Single Skill
Invoke any skill directly, outside the prompt file sequence
Quick updateMid-engagement
Recommended ▶
What it is
Invoke any single skill by name in a Claude Code session at any time, without running the prompt file sequence. The skill reads any existing specs in specs/ to operate in Review Mode if available, or runs Initialize Mode if starting fresh.
Where it goes
Skill files live in .claude/<skill-name>/SKILL.md. The skill is invoked via its trigger phrase or name in chat. No prompt file, no gate, no sequence — just the skill.
How it affects the process
Only that skill runs. No upstream or downstream impact unless the skill writes to a spec file that other skills depend on. Context files in context/ are still read at Step 0 if present. Fastest path for targeted changes.
How to invoke
Say the skill name in chat: “run spec-design”, “update the UI spec”, “run dev-copilot for the auth module”. The skill's trigger phrases are listed at the top of its SKILL.md file.
Example scenario
Mid-engagement, the client changes their database preference from PostgreSQL to MongoDB. You run spec-database directly to update that spec without re-running the full pipeline.
Trigger Mechanisms
T1
On-Demand (Manual Session)
Start a session and run when you're ready
StandardInteractive
Recommended ▶
What it is
The default mode. You open a Claude Code session and run skills or prompt files interactively. Fully manual, fully interactive. You control the pace and can pause, redirect, or restart at any point.
Where it goes
Any Claude Code session — desktop app, VS Code extension, or claude CLI. No scheduling setup required.
How it affects the process
Fully interactive. You see every output as it's generated. HITL gates are real-time. You can change direction mid-session. Most flexible but requires your presence throughout.
How to invoke
Open Claude Code, navigate to the project, and start the session. That's it.
Example scenario
Sitting down to run a spec session with a client on a call. You're guiding the output in real-time based on their feedback.
T2
Scheduled / One-Shot Trigger
Fire a prompt into a session at a specific time
DeferredAutomated start
Recommended ▶
What it is
Use create_trigger with a run_once_at timestamp or cron_expression to fire a prompt into a session at a future time. The trigger can resume an existing session (same conversation context) or spawn a fresh one.
Where it goes
Managed via the create_trigger MCP tool. Returns a trig_ ID that can be passed to update_trigger or delete_trigger to modify or cancel before it fires.
How it affects the process
The session fires at the scheduled time with the configured prompt as a user turn. If resuming an existing session, the full conversation context is available. If spawning fresh, the prompt must be self-contained.
How to invoke
Call create_trigger with name, prompt, and either run_once_at (RFC3339 timestamp) or cron_expression (hourly minimum). Optionally set create_new_session_on_fire: true for a clean session each time.
Example scenario
Post-meeting spec review: schedule a trigger to fire 30 minutes after a client call ends. The session resumes, summarizes what was decided, and drafts the next spec update automatically.
T3
/loop Recurring Execution
Self-paced recurring runs for ops-phase monitoring
RecurringPhase 05 ops
Recommended ▶
What it is
The /loop directive runs a prompt or skill on a recurring interval within a session. The model can self-pace (deciding when to fire next) or run on a fixed interval you specify. Primarily used with Phase 05 operational skills like ControlPlane and PatternExtractor.
Where it goes
Invoked in any Claude Code session via the /loop slash command. Specify an interval (e.g. /loop 30m /run-controlplane) or omit it for self-pacing. The session stays alive between iterations.
How it affects the process
Each iteration runs the target skill or prompt and waits for the next interval. Useful for monitoring deployed AI systems, running recurring evaluation sweeps, or any operational task that needs periodic re-execution. The conversation context accumulates across iterations.
How to invoke
In a session: /loop <interval> <prompt or skill>. Example: /loop 1h run ControlPlane health check and surface any anomalies. Stop by ending the session or using the task controls.
Example scenario
Deployed AI system is in production. You set a /loop 1h on the ControlPlane skill to monitor model drift, flag anomalies, and surface them in a running session log throughout the day.
