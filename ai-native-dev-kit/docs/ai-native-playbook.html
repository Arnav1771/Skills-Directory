Project Selection & Fit Criteria

AI-native delivery produces the highest ROI on well-bounded, well-specified projects. These criteria enable structured go/no-go decisions at intake.

Positive Selection Signals

  • ✓
    High domain documentation density — existing specs, ADRs, or design docs covering ≥70% of scope. Low ramp-up cost for context pack assembly.
    Required for L3
  • ✓
    Bounded scope with ≤3 service dependencies — cross-service blast radius is documented and manageable within pod authority.
    Strongly preferred
  • ✓
    High pattern reuse potential (≥60%) — similar patterns exist in AA skills registry, reducing novel context engineering effort.
    Velocity multiplier
  • ✓
    Single identified DRI — one accountable decision-maker who can resolve ambiguities in under 24 hours without committee escalation.
    Governance requirement
  • ✓
    2–12 week delivery horizon — time window matched to sprint cadence. Ultra-short (<2w) requires pre-built context packs already in inventory.
    Standard window

Disqualifying Signals

  • ✗
    No written specifications — purely tribal knowledge systems require a Context Sprint before pod activation.
    Needs prep
  • ✗
    Scope spans >5 services with undocumented dependencies — blast radius is uncontrolled, rework risk is unacceptable.
    Re-scope required
  • ⚠
    Regulatory or compliance requirements not screened — if present, human review gates become mandatory at every pipeline stage.
    Gate augmentation
03

Pod Team Structure

The AA delivery pod is the atomic unit of AI-native execution. Three human roles, multiple AI agent workstreams, one specification contract. Optimised for the L3 delivery standard.

🎯 Pod Lead

Owns the specification contract and context pack. Sole accountable party for delivery quality, gate decisions, and blast-radius management.

  • Assembles and maintains context packs
  • Orchestrates agent workstreams
  • Holds gate G1–G4 veto authority
  • Owns ADR log and skills registry contributions
  • Escalation point for spec ambiguity
⚡ AI Builder (×2)

Senior engineers operating Windsurf/Cursor IDE with Automation30 optimization layer. Responsible for code generation, skill execution, and agent output verification.

  • Executes spec-driven development workflow
  • Operates within assigned token budget
  • Flags spec ambiguities to Pod Lead
  • Contributes reusable patterns to skills registry
  • Participates in G3 conformance review
🤖 Automation30 Agent Layer

Orchestrator and specialist skill suite. Token budgeting, context management, and verification handled autonomously within defined thresholds.

  • CodeExtraction — skill boundary enforcement
  • SpecValidator — spec-to-code fidelity scoring
  • ContextPacker — dynamic context assembly
  • ReviewHarness — automated conformance checks
  • CostSentinel — real-time token budget tracking
The Irreplaceability Principle

The Pod Lead role cannot be replaced by AI in the current delivery model. Their function is not implementation oversight — it is context stewardship, specification integrity, and blast-radius authority. Removing this role does not accelerate delivery; it collapses quality at gate G3.

Spec-Driven Development (SDD) Methodology

SDD is AA's core delivery methodology. Every AI agent workstream is governed by a machine-readable specification. The specification is the source of truth — not the ticket, not the meeting notes, not the Slack thread.

OpenSpec YAML

Machine-readable specification format. Defines functional requirements, non-functional constraints, acceptance criteria, and skill boundaries in a single versioned artifact.

🗂️

Context Pack Engineering

Curated, token-budgeted context documents assembled per service boundary. Enables agent workstreams to operate within a defined information horizon without hallucinating domain facts.

🛡️

Skill Boundary Enforcement

Each Automation30 skill has a declared scope boundary. Cross-boundary operations are prohibited without explicit Pod Lead authorisation — preventing scope creep at the agent level.

SDD vs Traditional Requirements

Traditional agile stores requirements in Jira tickets and tribal knowledge. SDD stores them in versioned, machine-readable OpenSpec files that AI agents can directly parse, validate against, and report conformance scores on. This transforms "did we build what was asked?" from a subjective code review question into an objective numerical measurement.

Project Initiation & Gate Controls

Four mandatory gates govern pod activation, sprint execution, conformance verification, and delivery acceptance. Each gate has a binary pass/fail outcome and a defined accountable role.

GatePhasePass CriteriaOwnerFail Action
G1 · Intake Context Readiness Spec coverage ≥70%, DRI confirmed, context pack assembled, blast radius documented AA Executive + Pod Lead Context Sprint before pod activation
G2 · Sprint Start Pod Activation Token budgets allocated, skill registry confirmed, agent harness initialized, escalation path defined Pod Lead Halt; remediate missing prerequisites
G3 · Code Review Conformance Verification Automation30 conformance score ≥85%, no spec boundary violations, token cost within budget, no hardcoded secrets Pod Lead Halt; identify spec or context defect; re-submit
G4 · Release Delivery Acceptance All tests passing, ADRs logged, patterns extracted to registry, stakeholder acceptance obtained Pod Lead + Client DRI Do not release; remediate and re-verify
Gate Bypass Policy

Gate bypass is prohibited without CTO-level sign-off. Bypass carries an automatic post-mortem obligation within 5 business days. Repeated bypass events trigger a delivery model review for that pod.

AA Context Sprint Service

AA's Forward Deployment Engineers (FDEs) deliver a dedicated 2-week Context Sprint that elevates client systems from KM-0/KM-1 to KM-2 status — enabling immediate L3 pod activation. Outputs: OpenSpec YAML files, domain glossary, blast-radius map, and seed skills registry.

Operational Do's & Don'ts

Highest-signal operational rules derived from Automation30 delivery experience across enterprise engagements. These govern all active pods and are reviewed at every quarterly delivery retrospective.

✓ Do — Best Practices
  • Invest in specification quality before activating AI agents
  • Decompose every context pack at service domain boundaries
  • Log all architecture decisions as ADRs in real time during execution
  • Enforce gate G3 conformance score before any code proceeds to review
  • Treat rework rate as a leading indicator of context quality, not developer competence
  • Rotate API keys at every sprint boundary without exception
  • Extract reusable patterns to the skills registry immediately after each project
  • Maintain Pod Lead and AI Builder roles as structurally distinct at all times
  • Run context-only dry-runs before activating major agent workstreams
  • Maintain blast-radius documentation as a living artifact throughout the sprint
  • Use the Automation30 SpecImpactAnalyzer before any mid-sprint spec change
  • Escalate unresolvable spec ambiguities to the DRI within 4 hours
✗ Don't — Anti-Patterns
  • Activate AI-native delivery without KM-2 context coverage minimum
  • Bypass gate G3 to meet a deadline — context defects compound downstream
  • Allow AI agents to make structural architecture decisions autonomously
  • Reuse context packs from prior projects without reviewing for domain drift
  • Track token cost in aggregate only — always track at per-task granularity
  • Treat high rework rate as a developer performance problem
  • Conflate AI Builder code velocity with Pod Lead governance quality
  • Deploy agentic output without human verification at the G4 release gate
  • Scale a pod beyond 3 humans without a context re-architecture review
  • Use personal or shared API keys on production agent workstreams
  • Accept a spec change mid-sprint without running SpecImpactAnalyzer first
  • Treat the skills registry as a write-once archive — audit and prune quarterly
